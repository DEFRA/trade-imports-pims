# Plug-in and workflow migration log

This log records each migration of an existing plug-in or custom workflow activity (CWA) to the pattern decided in [ADR 0001](adr/0001-plugin-workflow-di-scaffold.md) and described in the [pattern guide](../docs/development/plugin-and-workflow-activity-pattern.md). Each entry states what kept its identity, where the logic now lives, what behaviour was preserved or changed, and which suspected defects were left in place for a later decision.

Every migration below is proven by unit tests only. None has been validated in a live Dataverse environment.

| Migration | Components | Remaining legacy |
| --------- | ---------- | ---------------- |
| 1 | `PopulateAnimalNumber` | |
| 2 | `FlagRecordOnWatchList`, `FlagRecordOnWatchListNotification` | |
| 3 | `AssociateWatchFlagsFromNotification`, `AssociateWatchFlagsFromPrimaryItahc` | |
| 4 | `DetermineInspectionRequirement` (plug-in and CWA), `InspectionPlaceOfOriginChange` (CWA) | 11 plug-ins and the other CWAs still use the legacy base classes. |

## 1. `PopulateAnimalNumber`

The first existing plug-in, `Defra.Imports.Plugins.ParameterSetKeyDataPair.PopulateAnimalNumber`, now follows the pattern.

- **Entry point identity:** the class name, namespace and assembly are unchanged, so the two registered steps (post-operation, synchronous `Create` and `Update` of `defraimp_parametersetkeydatapair`, with the `PreImage` on `Update`) need no re-registration. The `[CrmPluginRegistration]` attributes were removed in line with "Configure steps and images with the Plug-in Registration Tool, never code attributes". They were not read by any tool and had drifted from the solution metadata (execution order and the `Create` filtering attribute).
- **Layers:** the entry point stays `PopulateAnimalNumber` and keeps its handler name, `PopulateAnimalNumberHandler`, which sits beside it, but the work is generic. The handler projects the key data pair with the `ToApplyCommodityComplementKeyDataContext` extension method (`ParameterSetKeyDataPairExtensions`, in `Defra.Imports.Dataverse.Extensions`) onto a small immutable context (`ApplyCommodityComplementKeyDataContext`, in `Defra.Imports.Dataverse.Projections`) holding the key, the value and the importer notification and parameter set identifiers (with the parameter set name, if the reference carried one), and passes it to `ICommodityComplementKeyDataApplier.Apply` (`Defra.Imports.Application.CommodityComplements`). The applier owns the business rule, the explicit `Update` and the map of understood keys (`number_animal` to `defraimp_numberofanimals`). `CommodityComplementQueries` (`Defra.Imports.Dataverse.Queries`) holds the two early-bound LINQ queries that replaced the `QueryExpression` and `Retrieve` calls. The handler owns the `Update` pre-image merge, because it is a host concern. The key name is `KeyDataPairKeys.NumberOfAnimals` in `Application.Constants`.
- **Shared plug-in constants:** message names, stages, modes and the `Target` parameter name live in `Defra.Imports.Infrastructure.Plugins` (`PluginMessages`, `PluginStages`, `PluginModes`, `PluginInputParameters`) rather than as private constants in each handler.
- **Shared logging moved:** `ILogWriter`, `Severity` and `TracingServiceLogWriter` moved from `Defra.Imports.BusinessLogic.Logging` to `Defra.Imports.Infrastructure.Logging` and all unmigrated consumers were updated. `TimestampedTracingLogWriter` is a single-constructor subclass that the container can resolve and that timestamps messages as the legacy `Plugin` base class did. The unused `ConsoleLogWriter` and the legacy `AddSpeciesAnimalNumbers` were deleted.
- **Behaviour preserved:** the catch-and-continue contract for failures after the step contract is validated (each is traced as an error and swallowed), the warning messages, the unconditional `Update` and the use of the first pre-image whatever its name. Each is flagged with a code comment for investigation. The handler validates the registered step contract (entity, stage, mode, message, `Target`) before the catch and fails loudly with `InvalidOperationException`, surfaced as `InvalidPluginExecutionException`. This is an approved change in behaviour for a misconfigured registration only.
- **Items for later investigation (preserved, commented in code):** swallowing service faults inside a transaction, the unconditional `Update`, the first-match lookup with no `TopCount`, a pre-image overlay that nulls `defraimp_data` when the `Target` omits it, and use of the first pre-image whatever its name. The warning tag changed from `AddSpeciesAnimalNumbers` to `CommodityComplementKeyDataApplier` and the warning texts are now key-neutral (for example "Cannot apply key data pair 'number_animal' - …"); both are trace-only changes.

## 2. `FlagRecordOnWatchList` and `FlagRecordOnWatchListNotification`

The two plug-ins that flag a new ITAHC or importer notification on the active watch lists now follow the pattern.

- **Entry point identity:** `Defra.Imports.Plugins.Itahc.FlagRecordOnWatchList` and `Defra.Imports.Plugins.ImporterNotification.FlagRecordOnWatchListNotification` keep their names, namespaces and assembly, so the two registered steps (post-operation, synchronous `Create` of `defraimp_itahc` and `defraimp_importernotification`, filtering on the entity's own ID, no images) need no re-registration. The `[CrmPluginRegistration]` attributes were removed; they agreed with the solution metadata.
- **Layers:** each plug-in has a handler beside it (`FlagRecordOnWatchListHandler`, `FlagRecordOnWatchListNotificationHandler`) that validates the step contract, copies the `Target` with `ToEntity` and projects it with the `ToCreateWatchFlagsContext` extension method (`ItahcExtensions` and `ImporterNotificationExtensions`, one class per typed entity in `Defra.Imports.Dataverse.Extensions`) onto a small immutable context (`CreateItahcWatchFlagsContext`, `CreateNotificationWatchFlagsContext`, in `Defra.Imports.Dataverse.Projections`), which it passes to `IWatchFlagCreator` (`Defra.Imports.Application.WatchLists`). The extensions and contexts are in `Dataverse` rather than `Application` so that any future query class can reuse the projections without `Dataverse` depending on `Application`. The contexts hold only what the use case reads: a reference to the record, its name and the economic operator names. `WatchFlagCreator` owns the rules: the map from watch type to watch list lookup, the check order and the explicit `Create` of each `defraimp_watchflag`. `WatchFlagQueries` (`Defra.Imports.Dataverse.Queries`) holds the two early-bound LINQ queries that replaced the repository `Find` and the `QueryExpression`; `FindEconomicOperatorId` takes the watch type and selects the matching operator table, so no table or attribute name is held outside the generated model.
- **Contexts instead of entities:** a use case that needs only a handful of attributes takes a context rather than the whole typed entity, so its inputs are explicit and it cannot read or depend on attributes the handler did not intend to supply. The projection copies values, so the service cannot mutate the `Target`, and nothing forces a re-read. A `Create` `Target` holds only the attributes that were supplied, so a projected attribute that was not supplied reads as null, exactly as the legacy code read it; the projections do not validate that attributes are present. The pattern guide records this under "Projections and queries".
- **Deleted:** `FlagRecordsOnWatchListBase`, `FlagRecordParams`, `FlagRecordOnWatchListBusinessLogic`, `FlagRecordsOnWatchListNotificationBusinessLogic`, their `.projitems` entries and their two test classes (all five cases were ported).
- **Behaviour preserved:** the date filter, the single watch list read (made even when no identifier is given), the check order, interleaved reads and creates, one flag at most per identifier, the flag name built from the Target's name, and no catch.
- **Step-contract validation:** each handler validates the entity, stage (post-operation), mode (synchronous), message (`Create`) and `Target` and fails loudly with `InvalidOperationException`, surfaced as `InvalidPluginExecutionException`. This changes behaviour for a misconfigured registration only. Separately, `PluginBase` wraps any other failure in an `InvalidPluginExecutionException` (the legacy base let the raw exception escape), and the unused legacy trace writer is no longer created.
- **Items for later investigation (preserved, commented in code):** `DateTime.Now` (server local time, not UTC); no paging of the watch list read; the economic operator lookup has no ordering, so only the first operator with a name is checked; only the first matching watch list is flagged; no guard against duplicate flags; the flag name is "`<watch list> - `" when the `Target` omits `defraimp_name`.

## 3. `AssociateWatchFlagsFromNotification` and `AssociateWatchFlagsFromPrimaryItahc`

The two plug-ins that associate an import application with the watch flags of its primary importer notification or primary ITAHC now follow the pattern.

- **Entry point identity:** `Defra.Imports.Plugins.ImportApplication.AssociateWatchFlagsFromNotification` and `Defra.Imports.Plugins.ImportApplication.AssociateWatchFlagsFromPrimaryItahc` keep their names, namespaces and assembly, so the four registered steps (post-operation, synchronous `Create` of `defraimp_importapplication` filtering on `defraimp_importapplicationid`, and `Update` filtering on `defraimp_primaryimporternotificationid` or `defraimp_primaryitahcid`, no images) need no re-registration. The `[CrmPluginRegistration]` attributes were removed; they agreed with the solution metadata.
- **Layers:** each plug-in has a handler beside it (`AssociateWatchFlagsFromNotificationHandler`, `AssociateWatchFlagsFromPrimaryItahcHandler`) that validates the step contract, copies the `Target` with `ToEntity` and projects it with the `ToAssociateNotificationWatchFlagsContext` or `ToAssociateItahcWatchFlagsContext` extension method (`ImportApplicationExtensions`, in `Defra.Imports.Dataverse.Extensions`) onto a small immutable context (`AssociateNotificationWatchFlagsContext`, `AssociateItahcWatchFlagsContext`, in `Defra.Imports.Dataverse.Projections`) holding the import application ID and the primary record ID, if any. The handler owns the host rule that a `Create` without a primary record does nothing, so no read is made; an `Update` always calls the service. It passes the context to `IWatchFlagAssociator` (`Defra.Imports.Application.WatchLists`), which owns the use case: clear the link on the import application's watch flags that have the plug-in's lookup, then, if there is a primary record, link its watch flags that are not already linked, with an explicit `Update` for each. `WatchFlagQueries` gained four early-bound LINQ queries that replaced the repository `Find` calls and the string lookup name.
- **Deleted:** `AssociateWatchFlagsBase`, `AssociateWatchFlagsFromPrimaryItahcBusinessLogic`, `AssociateWatchFlagsFromPrimaryNotificationBusinessLogic`, their `.projitems` entries and their two test classes (all four cases were ported).
- **Behaviour preserved:** the order of reads and writes (read the linked flags, clear each, then read the primary record's flags and link each), the read of the linked flags even on a `Create`, the update payload (the watch flag ID and the import application lookup only), the condition for linking (the flag has no import application or a different one), unpaged reads, and no catch.
- **Step-contract validation:** each handler validates the entity, stage (post-operation), mode (synchronous), message (`Create` or `Update`, ignoring case) and `Target`, and fails loudly with `InvalidOperationException`, surfaced as `InvalidPluginExecutionException`. This changes behaviour for a misconfigured registration only: the legacy plug-in did nothing for any other message and did not check the entity, stage or mode. Separately, `PluginBase` wraps any other failure in an `InvalidPluginExecutionException` (the legacy base let the raw exception escape), and the unused legacy trace writer is no longer created.
- **Items for later investigation (preserved, commented in code):** a watch flag that stays linked is cleared and then linked again, so it is updated twice, which triggers downstream plug-ins, flows and audit; neither read is paged, so only the first page that Dataverse returns is used; a watch flag of the primary record that is linked to a different import application is moved to this one.

## 4. `DetermineInspectionRequirement`, `Workflows.DetermineInspectionRequirement` and `InspectionPlaceOfOriginChange`

The plug-in that determines the inspection requirement of an import application, and the two custom workflow activities that run the same logic, now follow the pattern. They were migrated together because they shared about 2,000 lines of legacy code, which was then deleted. The user approved extending the plug-in migration to the two activities for that reason.

- **Entry point identity:** `Defra.Imports.Plugins.ImportApplication.DetermineInspectionRequirement`, `Defra.Imports.Workflows.ImportApplication.DetermineInspectionRequirement` and `Defra.Imports.Workflows.ImportApplication.InspectionPlaceOfOriginChange` keep their names, namespaces and assembly. The three plug-in steps (synchronous `Update` post-operation filtering on `defraimp_primaryitahcid`, `defraimp_importrisklevelid`, `defraimp_placeoforiginid` and `defraimp_primaryimporternotificationid`, with `PreImage` and `PostImage` on the `Target`; `SetState` post-operation with both images on the `EntityMoniker`; `Delete` pre-operation with the `PreImage`) need no re-registration, and the activities keep their `Import Application` argument (required, referring to `defraimp_importapplication`). The `[CrmPluginRegistration]` attributes were removed; the plug-in's agreed with the solution metadata, and the activities' registration lives in the solution's plug-in assembly data.
- **Layers:** `DetermineInspectionRequirementHandler` (plug-in) validates the step, projects the images with `ImportApplicationExtensions.ToInspectionContext` onto an immutable `InspectionImportApplicationContext` (`Defra.Imports.Dataverse.Projections`) and makes one call to `IInspectionRequirementDeterminer.Determine`. Each activity has a handler beside it that passes the argument's identifier to `DetermineForImportApplication` or to `IInspectionPlaceOfOriginChanger.ChangePlaceOfOrigin`, which retrieve the import application with the same columns as before. `Defra.Imports.Application.InspectionRequirements` owns the use cases and their rules: `InspectionRequirementDeterminer` and `InspectionPlaceOfOriginChanger`; the risk level strategies (`P1`, `P2`, `P3`, `Tb` and `Unknown` `InspectionStrategy`, chosen by `InspectionStrategyFactory`); the counter managers (`AutonumberRiskCounterManager`, `OnlyGlobalCounterRiskCounterManager` and `PlaceOfOriginRiskCounterManager`, chosen by `RiskCounterManagerFactory`); and the writes (`AutonumberCounters`, `PlaceOfOriginCounters`, `InspectionRequirementUpdater` and `ImportRiskCounterAuditor`, each an explicit `Update` or `Create`). `InspectionQueries`, `AutonumberQueries` and `PlaceOfOriginQueries` (`Defra.Imports.Dataverse.Queries`) hold the early-bound LINQ queries that replaced the repository and `QueryExpression` calls. The counter manager's change event was replaced by a direct call to the auditor, which is equivalent because every manager had exactly one subscriber. The counter and risk level names moved to `InspectionConstants` (`Defra.Imports.Application.Constants`), with the names changed to PascalCase for StyleCop; the one other user, an integration test, was updated.
- **Contexts:** one context serves both use cases, because the place of origin change reads a subset of the same values. A working `InspectionRecord` wraps it and tracks the "counted" flag that the counter managers change, so the context itself is never modified. The legacy code changed the shared image entity.
- **Shared logging:** the workflow root registers `UntimestampedTracingLogWriter` (`Defra.Imports.Infrastructure.Logging`) as `ILogWriter`, because the legacy workflow base wrote trace messages without timestamps. The plug-in root keeps the timestamped writer.
- **Constants:** `PluginMessages.SetState`, `PluginMessages.Delete` and `PluginInputParameters.EntityMoniker` were added and pinned in `PluginConstantsTests`. The image names `PreImage` and `PostImage` are registration-specific, so they stay private to the handler.
- **Deleted:** `DetermineInspectionRequirementBusinessLogic`, `InspectionPlaceOfOriginChangeBusinessLogic`, `CommodityHelper`, `InspectionRequirement`, the five `DetermineInspection` strategies and their factory, `DetermineInspectionContext`, the risk level counter managers, auditor and counter transaction detail types, and `ImportApplicationConstants`, with their `.projitems` entries and their eight test files (the orchestration test class had no active cases; every active case of the others was ported, and the skipped cases were rewritten as running tests). The autonumber, place of origin and configuration parameter repositories remain, because other unmigrated code uses them.
- **Behaviour preserved:** the order of reads and writes, including the reads made when a counter manager is created (the risk level name twice, the gold/bronze rules, the autonumbers and the place of origin) whether or not the manager is used; every counter update and counter history record; the outcome payload (including the declined reason and the original values) written even when unchanged; the log messages and the `DetermineInspectionLogic` tag; the use of the risk level name from the post-image and a read by identifier for the pre-image; the creation branch, which only the workflow activity reaches; the columns that each activity retrieves; and no catch anywhere.
- **Step-contract validation:** the plug-in handler validates the entity, mode (synchronous), message (`Update`, `SetState` or `Delete`, ignoring case), stage (post-operation for `Update` and `SetState`, pre-operation for `Delete`), the `Target` (an entity for `Update`, a reference for `Delete`) or `EntityMoniker` (a reference), and the images (`PreImage` always, `PostImage` except for `Delete`). It fails loudly with `InvalidOperationException`, surfaced as `InvalidPluginExecutionException`. This changes behaviour for a misconfigured registration only: the legacy plug-in treated a missing `PostImage` as a deletion. The activity handlers add no validation. Separately, `PluginBase` wraps any other plug-in failure in an `InvalidPluginExecutionException` (the legacy base let the raw exception escape), and the unused legacy trace writer is no longer created. The workflow activities now follow `WorkflowActivityBase`, so failures are traced and rethrown unchanged.
- **Items for later investigation (preserved, commented in code):** `DetermineInspectionRequirement` (activity) and `InspectionPlaceOfOriginChange` retrieve columns that omit the import application type, so the strategies treat the record as having no certificate and write nothing for P1, P2, P3 and TB; references are compared by object when the place of origin is checked for a change, so an unchanged place counts as changed; deactivation and deletion fail when the record had no risk level, because there is no counter manager; a missing coverage rule, place of origin, configuration parameter or autonumber fails with a null reference, or a parsing error for the TRACES setting; the decrement of an autonumber counter records the quota counter's values in its history; taking a quota flags the record as counted, and setting a place of origin's quota sets its application counter; the catch of `NullReferenceException` in the gold/bronze check cannot catch the `TargetInvocationException` that the query provider throws; lookups of autonumbers, coverage rules and gold/bronze rules take the first match with no ordering; and counters and flags are updated unconditionally, which triggers downstream plug-ins, flows and audit. Culture-sensitive `ToLower` calls on risk level names became `ToLowerInvariant`, which does not change the result for the ASCII names in use.

## Changes to the scaffold after the migrations (2026-11-19)

These changes followed a review of the pattern. None alters the behaviour of a migrated component.

- **Illustrative example removed.** The watch list initialisation example (a plug-in, a CWA, their handlers, `IWatchListInitialiser`, `WatchListQueries` and `WatchListInitialisationContext`), its registrations and its tests were deleted, because the migrated components now serve as the reference. No step or activity registration referred to it. `EntityExtensions` was kept, because `PopulateAnimalNumberHandler` uses it.
- **Activity binding moved into the base class.** `WorkflowActivityBase<THandler>` now registers the activity under its concrete type itself, through a new `PluginContainer.Register(Type, object)` overload. The `RegisterActivity` override was removed from `DetermineInspectionRequirement` and `InspectionPlaceOfOriginChange`.
- **Shared inspection registrations.** `InspectionRequirementRegistrations.AddInspectionRequirements` (`Defra.Imports.Application.InspectionRequirements`) registers the inspection services and queries for both heads. As a result the plug-in root now also registers `IInspectionPlaceOfOriginChanger`, which no plug-in handler requests.
