# 0001. Lightweight DI Scaffold for Dataverse Plug-ins (Application / Dataverse / Infrastructure Shared Projects)

- **Status**: Proposed — the composition/scoping scaffold, the synchronous `PluginBase<THandler>` adapter and the generic `WorkflowActivityBase<THandler>` workflow adapter are now implemented and unit-tested on this branch, conforming to this recommendation's synchronous `void Execute()` contract (the earlier `Task`-based handler contract, its sync-over-async bridge and its tests have been removed; the illustrative handler is utility-named `WorkOrderInitialisationHandler`). This remains unapproved, **proposed** architecture: no real plug-in/CWA has adopted the pattern, no component is registered with Dataverse or included in a solution, and effective-identity/deployed-host behaviour has not been validated in an isolated environment. Seek normal review approval before any production adoption. **Model migration update (2026-10-22):** the one-off migration of the legacy `Defra.Imports.Model` Shared Project is complete — the generated early-bound types now live in `Defra.Imports.Dataverse` (namespace `Defra.Imports.Dataverse.Model`), `Constants` and `ReferenceData` live in `Defra.Imports.Application`, and the `Defra.Imports.Model` project has been removed. This is a structural move only; it does not change the Proposed status of the DI pattern.
- **Date**: 2026-10-22
- **Related requirement(s)**: The explicit user requests to scaffold separated application, Dataverse and infrastructure Shared Projects with execution-scoped DI, retain the non-deployed Container, add a handler-first `WorkflowActivityBase<THandler>`, and define migration refinements for analyser warnings, model ownership, handler placement and application-service responsibilities. The initial scaffold did not migrate existing business logic; these refinements govern subsequent capability migrations. No Epic/Feature/User Story or `AB#` was supplied; no work-item traceability is invented.
- **Related ADR(s)**: None. This is the first substantive ADR in the repository; `0000-template.md` is the template only.
- **Decision confidence**: **High** that a synchronous `void Execute()` handler contract is the simplest fit: Dataverse invokes plug-ins synchronously, the SDK calls used here are synchronous, and there is no requirement for asynchronous work — both `IPluginHandler.Execute()` and `IWorkflowActivityHandler.Execute()` are now implemented this way, with the `Task` contract, its blocking bridge and its Task-specific assertions removed. **High** for the composition/scoping mechanics, based on both deployment heads building in Release with no errors (the scaffold introduced no SA1642/SA1615 warnings; unrelated repository warnings remain outside its scope — see Fitness Check) and the full `Defra.Imports.UnitTests.Infrastructure` suite passing (41/41, 0 failed, 0 skipped — see Fitness Check for the exact command). **Medium** for the now-implemented `WorkflowActivityBase<THandler>` adapter: concrete-activity/context injection, argument access, concurrency isolation and execution/cleanup failure precedence are implemented and unit-tested — including driving the activity through a real `System.Activities.WorkflowInvoker` — but no activity is registered with Dataverse and no isolated-environment/registered execution has validated host behaviour, so confidence remains Medium pending that adoption. **Medium** for the identity-aware provider/context factory: implemented and unit-tested against requested factory arguments only (mocks, including an executing-user `Guid.Empty` case), not effective Dataverse caller/impersonation. ## Context

### Current pattern (as found)

- Business logic and data access were originally compiled from three **Shared Projects** (`.shproj`/`.projitems`): `Defra.Imports.Model`, `Defra.Imports.BusinessLogic`, `Defra.Imports.Repositories`. `Defra.Imports.Model` has since been retired (see the migration update in Status); the original three-project description is retained here as the baseline this decision was made against.
- These are imported into two deployed, sandbox-registered head assemblies — `Defra.Imports.Plugins` (17 plug-in classes, all deriving from `Defra.Imports.BusinessLogic.Plugin`) and `Defra.Imports.Workflows` (custom workflow activities using multiple base-class families, including the workflow-head `WorkflowActivity`, the shared `BusinessLogic.WorkflowActivity` and `WorkFlowActivityBase`) — and into a third, **non-deployed** assembly, `Defra.Imports.Container`, referenced only by `Defra.Imports.UnitTests`.
- Both head `.csproj` files already use a **configuration-conditional import**: the three shared projects are compiled directly into `Plugins`/`Workflows` only when `$(Configuration) != 'UnitTest'`; under `UnitTest` they instead take a `ProjectReference` to `Defra.Imports.Container.dll`. This keeps the Release/Debug deployed assemblies self-contained (no dependency on an external DLL inside the Dataverse sandbox) while giving unit tests one shared, directly-referenceable copy of the business logic types.
- There is **no dependency injection** today. `Plugin.Execute` manually `new`s a `RepositoryFactory` and `TracingServiceLogWriter` per call and passes them as parameters into an abstract `Execute(...)` method; concrete plugins then manually `new` their business-logic classes.
- An **unused, dead scaffold** already exists: `Defra.Imports.Plugins.PluginBase` (non-generic, with `ILocalPluginContext`/`LocalPluginContext`/`LocalTracingService`), defined but never derived from by any of the 17 real plugin classes — confirmed by a repository-wide reference search. It represents an earlier, abandoned attempt at the same problem this ADR addresses.

### Platform constraints that govern this decision

Verified against current Microsoft Learn guidance:

- **No asynchronous or parallel execution inside plug-ins or CWAs.** Dataverse's "[Don't use parallel execution within plug-ins and workflow activities](https://learn.microsoft.com/power-apps/developer/data-platform/best-practices/business-logic/do-not-use-parallel-execution-in-plug-ins)" best practice explicitly lists the **Task-based Asynchronous Pattern, Task Parallel Library, and managed threading** as unsupported inside plug-in/CWA code — not just literal `Thread`/`Task.Run` use. The proposed handler contract is synchronous `void Execute()`; it must not use `async void`, background work, or parallel SDK calls.
- **`IPlugin` instances are cached and may be invoked concurrently** by multiple worker threads against the *same* instance ("[Develop IPlugin implementations as stateless](https://learn.microsoft.com/power-apps/developer/data-platform/best-practices/business-logic/develop-iplugin-implementations-stateless)"). Any shared/static state (including a composition root) must be safe under concurrent `Execute` calls.
- **`ILogger` (`Microsoft.Xrm.Sdk.PluginTelemetry.ILogger`) is plug-in-specific, environment/feature-flag dependent** (only populated when an admin has enabled Application Insights integration for the environment) and undocumented for custom workflow activities; the existing `WorkFlowActivityBase.LocalWorkflowContext` only ever pulls `IWorkflowContext`, `ITracingService`, `IOrganizationServiceFactory` from `CodeActivityContext.GetExtension<T>()` — there is no workflow equivalent of `ILogger`.
- A synchronous plug-in step has a **2-second practical budget and a hard 2-minute ceiling** for the whole message operation ("[Analyze plug-in performance](https://learn.microsoft.com/power-apps/developer/data-platform/analyze-performance)") — scope construction/teardown cost is a real, bounded design constraint, not a theoretical one.

## Decision

Introduce three additional Shared Projects — **`Defra.Imports.Application`**, **`Defra.Imports.Dataverse`**, **`Defra.Imports.Infrastructure`** — alongside the existing `BusinessLogic`/`Repositories` (and, at the time of the original decision, `Model`, which has since been retired), imported into `Plugins`, `Workflows`, and `Container` using the **same configuration-conditional pattern already in place** (self-contained in Release/Debug, routed through `Container.dll` under `UnitTest`). The initial scaffold implementation changes no deployed plug-in/CWA registration and migrates no existing business logic. As capabilities are subsequently migrated, apply the layer ownership, handler boundary and analyser-cleanup requirements below; the small structural moves are part of that migration rather than a separate rewrite.

### Confirmed migration constraints

The user confirmed the following decisions during review. They govern subsequent capability migrations, not a business-logic rewrite within the initial scaffold. **Decision confidence: High** for the intended constraints because they are explicitly confirmed; implementation conformance still requires verification. The ADR remains proposed overall.

- **Behaviour and bug approval:** migrated code must behave the same even when substantially restructured. Preserve workflow output names, types and values; target mutations; database effects; execution identity; transaction behaviour; and error contracts. Raise suspected bugs and questionable practices for an explicit decision; do not fix them silently during refactoring. Preserve existing catch-and-continue behaviour pending that decision, including structured error outputs and diagnostic field values. Preserve deliberate business exceptions and user-visible messages.
- **Existing entry-point identity:** retain concrete plug-in and workflow activity class names, namespaces and assembly identity so existing registrations and workflow references remain valid. Preserve registration metadata: message, stage, mode, execution order, filtering attributes, image names/columns and impersonation settings. Preserve activity argument metadata, types, names and defaults. No step re-registration or workflow reconfiguration is part of migration. Utility-based naming applies to new entry points only, not renaming existing registered types; internal handlers/services may be renamed or replaced. Normal assembly versioning and deployment still apply.
- **Persistence and transactions:** the handler determines whether a change is made through the actual pipeline target or an explicit update call, while preserving the existing operation's observable behaviour and write timing. Do not copy target changes into a disconnected entity or introduce an extra update as a refactoring convenience. Keep transaction control with Dataverse; do not add automatic `SaveChanges()` on disposal, new transaction wrappers, added retries or deferred writes.
- **Identity and context lifetime:** unqualified `IOrganizationService` and `ImportsContext` mean the executing user. No implicit elevation, identity changes or fallback to another user; unsupported workflow identity requests fail explicitly. Any alternative privileged operation requires a separate reviewed design. Contexts remain independent unless shared tracking is demonstrably required; any sharing is restricted to one invocation and one identity.
- **Ownership:** the scope disposes container-created disposable objects; it never disposes host-provided SDK services, the activity or its execution context. Callers dispose explicitly factory-created contexts within the invocation. Do not allow deferred queries or context-backed results to escape their owner's lifetime. These rules also apply to contexts created inside migrated repositories/utilities: resolving their parent factory through DI does not automatically make nested objects container-owned.
- **Workflow extension overrides:** the custom `IFetchService` extension overrides were introduced only to substitute dependencies in tests, not as production contracts. Replace these seams with test-specific DI composition when migrating their activities; do not reproduce custom extension lookup/override precedence in the new base. Continue retrieving genuine SDK runtime extensions through `CodeActivityContext.GetExtension<T>()`. Test composition must not mutate the frozen production root or introduce a process-wide override that leaks between tests.

### Execution and cleanup failure precedence

Both host adapters must apply the following policy, including activation, handler execution and workflow argument mapping:

1. If execution fails, preserve that failure as primary, including deliberate business exceptions/messages. Attempt all remaining scope cleanup; trace cleanup failures separately without replacing the execution failure. This policy does not authorise a new generic wrapper that changes an existing deliberate business error contract.
2. If execution succeeds but cleanup fails, surface the cleanup failure; multiple cleanup failures may be aggregated. Cleanup must not become a silent success.
3. A failure while tracing a secondary cleanup error must not replace the primary execution error. Preserve secondary diagnostic information where possible; do not introduce a broad catch that silently hides execution failures.

The existing container attempts all owned disposal and aggregates failures; both adapters now explicitly preserve the primary execution failure and its stack (via `ExceptionDispatchInfo.Capture(...).Throw()`) ahead of a disposal failure, and surface a cleanup-only failure as an `AggregateException` once all cleanup has been attempted. This is implemented and unit-tested in both `PluginBase<THandler>` (`ScopedPluginBaseTests`) and `WorkflowActivityBase<THandler>` (`WorkflowActivityScaffoldTests`), covering execution-only failure, cleanup-only failure, simultaneous failure, and continuation through three throwing disposals; a further test confirms a tracing failure while reporting a cleanup failure does not replace the primary execution exception. For the plug-in adapter, the 3-inner-exception `AggregateException` surfaces directly as `InvalidPluginExecutionException.InnerException`. For the workflow adapter, the adapter itself throws that same 3-inner `AggregateException` — confirmed by the exact exception traced via `ITracingService` — but the real `System.Activities.WorkflowInvoker` used in the test translates it on the way out: the exception that reaches the caller of `WorkflowInvoker.Invoke` carries only the first inner cleanup exception, not the full aggregate. Be precise about this runtime translation when relying on the surfaced exception type/shape from a `CodeActivity` host. This agreed infrastructure policy does not silently change handler-level catch-and-continue contracts.

### Layer ownership and migration boundaries

- **Model contents live with their owning layer (migration complete).** Entity/model, message, option-set and other Dataverse schema-bound types are in the `Dataverse` Shared Project, using the generated `Defra.Imports.Dataverse.Model` namespace (Dataverse Model Builder output; hand-written types must not be placed in it, because regeneration may overwrite them). Hand-written query result projections (for example `WorkOrderInitializationContext`) live beside the query that returns them in `Defra.Imports.Dataverse.Queries`. `Constants` and `ReferenceData` live in `Application` under `Defra.Imports.Application.Constants` and `Defra.Imports.Application.ReferenceData`. The old `Defra.Imports.Model` Shared Project has been retired, with all shared-project imports/references updated in the same change; a repository search finds no remaining reference to it outside historical documentation. Do not reintroduce a parallel model project, duplicate type definitions or parallel namespaces; add new schema types by regenerating into `Defra.Imports.Dataverse.Model`.
- **Keep host handlers in the deployed head that owns the entry point.** Plug-in handler classes belong in `Defra.Imports.Plugins`, not the shared `Application` project: they are not shared and depend on plug-in context/step concerns. Workflow activity handlers remain beside their concrete activities in `Defra.Imports.Workflows` where they depend on activity types and `CodeActivityContext`. Shared application services are called by handlers, not used as a home for handlers.
- **Handler responsibilities are adapter/orchestration responsibilities.** A plug-in handler validates the execution context against the expected registration contract (such as message, primary entity, stage and required images/parameters), performs plug-in-specific work on the execution context (including target mutations and shared-variable updates), handles relevant tracing/SDK-boundary concerns, then chooses and calls coarse, use-case-shaped application methods. Choosing between methods is a handler concern: for example, calling a method that hydrates the pipeline target in place (so the pipeline persists it) rather than one that issues an explicit `Create`/`Update`, as the observable write behaviour must be preserved. A handler should call one or two such methods and must not sequence read → decide → write flow itself: branching on domain data, multi-step query/update sequences and other business flow belong in a single application method. It should not absorb reusable business rules, query construction or persistence implementation. Workflow handlers similarly adapt activity arguments/context and choose application methods, while preserving the activity contract.
- **Application classes own reusable use-case logic, not host plumbing.** Application services should not depend on a plug-in class, `IPluginExecutionContext`, `CodeActivityContext` or entry-point handler. They own whole use cases, including their reads and writes, and may take `IOrganizationService` (or an `ImportsContext`) directly: the Application layer already depends on the Dataverse SDK and early-bound types, so a per-entity reader/writer interface would add interfaces, implementations and registrations without hiding a dependency, and `IOrganizationService` can already be faked in tests. Extract a shared query class into the `Dataverse` project only where a query is reused or is difficult to fake (for example, paging, `ExecuteMultiple` or non-trivial `QueryExpression`/FetchXML construction), not as a mandatory layer. Keep methods explicit about persistence: a command such as `recordCloner.CreateClone(Entity row)` means a Dataverse create is performed; an operation such as `workOrderInitialiser.GetInitialisedWorkOrder(msdyn_workorder workOrder)` returns a hydrated entity for the caller to use (for example, as the existing pre-operation target) and does not issue a create/update. Do not infer that every `Get...` method makes a database read: document the side-effect contract and cover it in tests. Because `Entity` is a mutable reference, a service can operate on whatever entity it is given (the pipeline target or a retrieved entity) without knowing which; the handler's choice of method and argument determines whether the pipeline or an explicit call persists the change. Do not introduce a write-abstraction port to express that choice.
- **Keep the migration vertical and behaviour-preserving.** Move a selected use case's handler, application logic and Dataverse dependencies together, update namespaces and `.projitems` ownership atomically, and remove old inclusions. Do not migrate every legacy class merely to complete the scaffold; preserve the existing entry-point identity and registration contracts.

### The composition model

1. **`PluginContainer`** (`Defra.Imports.Infrastructure.DependencyInjection`) is an instance class with two states, both represented by the same type:
   - **Root** — created with `new PluginContainer()`. `Register<TInterface, TImplementation>()` / `Register<TImplementation>()` register a **type pair** (not a factory delegate); resolution builds the graph via reflection, requiring **exactly one public constructor** per implementation and detecting circular dependencies by walking the resolution path. Root registrations are mutable until the **first** `CreateExecutionScope()` call, after which they are **frozen** — further `Register` calls throw `InvalidOperationException`.
   - **Execution scope** — returned by `root.CreateExecutionScope()` as an independent `PluginContainer` holding a **copy** of the root's type registrations. Only a scope (never the root) accepts `Register<TService>(instance)` — a **borrowed** runtime instance (e.g. the current `IOrganizationService`) that the container will never dispose. Attempting to borrow-register on the root, or to create a scope from a scope, throws explicitly.
   - All operations are guarded by an internal lock, making concurrent `CreateExecutionScope()`/`Resolve<T>()` calls against one cached, shared root safe — directly answering the "stateless/concurrently-invoked `IPlugin`" constraint above. A 30-iteration `Parallel.For` test and a 10-iteration concurrent-`Execute` test both confirm no cross-execution state leakage.
   - **Constructor-created services are transient** and tracked for disposal; a scope's `Dispose()` disposes them in **reverse construction order**, continues past individual disposal failures (aggregating them into an `AggregateException` rather than abandoning cleanup), and **never** disposes borrowed instances. Partial-activation cleanup is covered: if a later dependency in a graph fails to construct, everything already constructed earlier in that same `Resolve<T>()` call is still tracked and is still disposed when the enclosing scope disposes.
   - `Resolve<T>()` is callable on the root directly for registrations that need nothing execution-scoped (validated by test); production code must still resolve the **handler graph** from the scope, because the only correct place to find the current invocation's borrowed `IOrganizationService`/`ITracingService`/context is the scope — attempting it from the root fails structurally (no registration exists there), not by convention alone.

2. **`PluginBase<THandler>`** (`Defra.Imports.Infrastructure.Plugins`), `where THandler : IPluginHandler`, is the generic adapter real plugin classes derive from. It:
   - Takes a `PluginContainer` (the frozen root) via a **protected constructor** — `protected PluginBase(PluginContainer container)`.
   - Implements `IPlugin.Execute(IServiceProvider)` by creating **one execution scope per call**, registering the four execution-scoped borrowed instances (`IPluginExecutionContext`, `IOrganizationService` for the step's executing user, `ITracingService`, and the thin `IPluginExecution` wrapper), conditionally registering `ILogger` **only if Dataverse actually supplied one**, resolving `THandler` from the scope, and invoking its synchronous `void Execute()` directly. There is no Task-returning handler contract, sync-over-async bridge, or continuation to manage.
   - Fails explicitly (`InvalidOperationException`, wrapped as `InvalidPluginExecutionException`) if Dataverse does not supply a required runtime service (`ITracingService`, `IPluginExecutionContext`, `IOrganizationServiceFactory`, or the organisation service itself) — there is no silent null/no-op fallback for anything mandatory. `ILogger` is the one deliberate exception: it is registered **only when present**; a handler that declares a hard constructor dependency on `ILogger` will fail resolution with a clear message when it is unavailable, rather than receiving a null or no-op logger. This pushes a design discipline onto handler authors: a handler meant to be portable to a CWA-style scope (see below) must not take a hard `ILogger` dependency, because no CWA entry point will ever register one.
   - `IPluginExecution` is deliberately **thin**: `Context`, `Service`, `Tracing` only — not the seven-member `ILocalPluginContext` the dead scaffold proposed. Handlers that need something else (e.g. a specific query class) take it as its own constructor dependency rather than reaching through a God-context object.

   **Composition-root ownership:** use one registration-only root for the entire `Plugins` head assembly, shared by all its concrete plug-in classes. Adding a plug-in means adding its handler and any new service registrations to that root, not creating a new root or copying the common registrations. Each plug-in invocation still gets a fresh execution scope. `Workflows` is a separate deployed head assembly and therefore cannot share the same static root instance; if CWAs adopt the pattern, use one root for that assembly, shared by its activities. Common registration code may be factored into a shared helper if both heads need it, while each head creates its own root.

   **Plug-in naming and registration:** for new entry points, name concrete `IPlugin` entry-point classes after the utility or capability they provide (for example, `WorkOrderInitialisationPlugin`), not after a particular Dataverse message, stage, execution mode, or filtering condition. Configure those step-specific details using the Plug-in Registration Tool, not code attributes; one utility-named class may have multiple registered steps where it implements the same utility. The entry-point name is independent of its handler type. Existing registered class names, namespaces and assembly identity remain unchanged during migration.

3. **CWAs use handler-first DI through a workflow-specific adapter.** The additive `Defra.Imports.Infrastructure.Workflows.WorkflowActivityBase<THandler> : CodeActivity`, with `where THandler : IWorkflowActivityHandler`, is now implemented. The new `IWorkflowActivityHandler` contract declares synchronous `void Execute()`. Existing workflow base classes and activities remain untouched; no existing activity has migrated to this adapter. The implemented adapter:
   - Accepts the registration-only root through a protected constructor. Every concrete activity has a public parameterless constructor passing the same `WorkflowCompositionRoot.Root`, defined once in the `Workflows` head assembly, not once per activity or closed generic type. The root registers handler and service types only; it never registers or constructs the host-created activity as a service implementation.
   - Overrides `CodeActivity.Execute(CodeActivityContext)` as a sealed override, validates the context and required extensions, and creates one scope per invocation. It retrieves `IWorkflowContext`, `IOrganizationServiceFactory` and `ITracingService` through `GetExtension<T>()`, creates the organisation service for `IWorkflowContext.UserId`, and registers `IWorkflowContext`/`IOrganizationService`/`ITracingService` as borrowed instances. Missing required services fail explicitly; there is no silent fallback or change of executing user.
   - Borrow-registers the current `CodeActivityContext` in the scope and calls `protected abstract void RegisterActivity(PluginContainer scope)` before resolving the handler. The concrete override contains only `scope.Register<ConcreteActivity>(this)`, preserving the concrete type without reflection, dynamic dispatch or unsafe self-casts. This binds the exact host-created activity, not another activity instance. The existing container resolves instance registrations by exact type, so registering only `CodeActivity` would not satisfy a handler constructor requiring the concrete activity.
   - Resolves `THandler` and calls `Execute()` directly. The handler receives the concrete activity, `CodeActivityContext` and whichever application/query services it requires through constructor injection. It reads and validates public `InArgument<T>` values with the current context, invokes application services and writes public `OutArgument<T>` values with that same context. Concrete activities declare argument metadata and the type-binding override only; they contain no business logic or input/output mapping.
   - Traces failures when tracing is available and rethrows them without suppressing the original cause; disposes the scope after handler execution, including argument access and exception paths, using the agreed execution/cleanup failure precedence below. Activity and context are borrowed, host-owned instances and are never disposed by the container. Resolved handlers and container-created disposable services belong to the invocation scope. Never cache a handler, scope, context or resolved service on the activity/root; never mutate activity argument-property definitions or store execution values on the activity. Read/write argument values through the current context only, including concurrent invocations of the same cached activity.
   - Does not manufacture `IPluginExecutionContext`/`IPluginExecution`, require `IPluginHandler`, register plug-in telemetry `ILogger`, or introduce asynchronous execution. The shared infrastructure source and any required `System.Activities` framework reference must follow the existing shared-project/UnitTest import pattern when implemented. Concrete workflow handlers belong alongside their activities in the `Workflows` head project because they depend on those head-specific activity types. Application services remain in `Application` and independent of workflow activity/context types.

   **Why handler-first:** the container constructs the complete handler dependency graph rather than selecting one application service for a callback. Activities remain declarative entry points; workflow handlers own argument adaptation and orchestration, while application services remain reusable from plug-ins. This adds one small synchronous handler contract and a concrete-activity binding override, not a generic input/output framework. Unit tests now drive the implemented adapter through a real `System.Activities.WorkflowInvoker`, verifying exact concrete-activity binding, argument mapping, reused/concurrent-invocation isolation and execution/cleanup failure precedence; no registered activity or isolated-environment execution has yet verified it.

### Execution identity and identity-bound contexts (implemented; effective Dataverse identity not yet validated)

**Default identity:** an unqualified `IOrganizationService` means the current **executing user**, not necessarily the initiating user. The plug-in adapter uses `IPluginExecutionContext.UserId`; the workflow adapter uses `IWorkflowContext.UserId`. This is host-provided service impersonation, not a new authenticated connection. An injected, unqualified `ImportsContext` must be constructed over that default service; its constructor does not independently select or elevate identity. Register `ImportsContext` as a concrete type when required so the container constructs it with the invocation's default `IOrganizationService` and owns its disposal. Like other constructor-created services in this container, it is transient, not a shared tracking context.

**Host-specific capabilities:** the Microsoft SDK documentation for [CreateOrganizationService](https://learn.microsoft.com/en-us/dotnet/api/microsoft.xrm.sdk.iorganizationservicefactory.createorganizationservice?view=dataverse-sdk-latest) explicitly distinguishes plug-ins from custom workflow activities. [Plug-in impersonation guidance](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/impersonate-a-user) further distinguishes the executing and initiating users.

| Requested identity | Plug-in factory behaviour | Custom workflow activity factory behaviour |
| ------------------ | ------------------------- | ----------------------------------------- |
| Executing user | Pass `context.UserId`; `Guid.Empty` also means the plug-in execution context's `UserId`. | Calls use the workflow execution context's `UserId`. |
| Initiating user | Pass `context.InitiatingUserId`. | Passing `InitiatingUserId` is not a documented identity switch: calls still use workflow `UserId`. If both IDs coincide, the executing-user service already represents that user. |
| SYSTEM | Pass `null`. | Do not interpret `null` as SYSTEM: the documented workflow behaviour remains execution as workflow `UserId`. |
| Specific user | Pass the selected valid system-user ID, subject to platform permissions. | Do not assume passing another ID changes identity: the documented behaviour remains execution as workflow `UserId`. |

**Explicit identity dependencies:** an invocation-scoped identity-aware provider, `IExecutionServiceProvider`, is implemented with clearly named operations for executing user, initiating user and SYSTEM. There is no arbitrary-user selection API; only these three named operations exist. Separate plug-in (`PluginExecutionServiceProvider`) and workflow (`WorkflowExecutionServiceProvider`) implementations are used rather than a common implementation that simply passes different IDs to the SDK factory. The appropriate provider is bound as an invocation-local, borrowed instance in each host adapter (`PluginBase<THandler>.Execute`/`WorkflowActivityBase<THandler>.Execute`); it uses that invocation's factory/context and is never cached in the static root. The container already supports borrowed-instance bindings; a named/keyed-registration framework was not required.

- Keep plain `IOrganizationService` executing-user-only even when a handler requests another identity. Do not replace its binding mid-execution or change the identity of an existing context.
- A component requiring another identity injects the explicit provider and requests that identity deliberately. SYSTEM use requires a narrowly scoped, reviewed business justification; never retry an access-denied operation as SYSTEM or silently fall back to a different user.
- A workflow provider returns only identities it can actually supply using supported host behaviour. A request for an unsupported identity fails explicitly with `NotSupportedException` before business calls, is traced by the adapter when possible and propagates through its normal error path. Do not return an executing-user service while claiming it represents SYSTEM or a different initiating user.
- Do not establish an external connection, introduce credentials or rely on undocumented impersonation behaviour to make the two hosts appear equivalent. A workflow requiring another identity needs a separately validated design using supported workflow execution configuration or a separately scoped operation, with security review and its ALM path recorded before adoption.

**Identity-bound `ImportsContext` creation:** where a context is needed for a non-default identity, an explicit `IImportsContextFactory`/`ImportsContextFactory` is implemented in the Dataverse layer that depends on the identity-aware provider and constructs `ImportsContext` over the selected service (`CreateForExecutingUser`/`CreateForInitiatingUser`/`CreateForSystem`). Contexts returned by this factory are **caller-owned** and must be disposed with `using` within the invocation; they are not automatically tracked by the container merely because their factory was resolved from it. The factory does not own or dispose borrowed host services. Never reuse a context or its tracked entities across identities, invocation scopes or concurrent operations. The provider contract/host adapters remain in infrastructure and application-service identity requirements explicit; business services must not obtain the container or a raw service locator.

**Alternatives:** multiple unqualified service registrations are rejected because the container has one binding per exact type and identity would be ambiguous. A single SDK-factory wrapper assuming identical identity semantics across hosts is rejected because the documented workflow behaviour differs. Explicit provider operations preserve an executing-user default and surface unsupported capabilities without introducing a new connection or a generic keyed-container extension.

**Decision confidence: High** for the documented host distinction and executing-user default; **Medium** for the implemented provider/context-factory integration — unit-tested (`ExecutionServiceProviderTests`) for exact factory arguments (executing/initiating `Guid` and `null` for SYSTEM on the plug-in side; executing-user default plus explicit rejection of a different initiating user and of SYSTEM via `NotSupportedException` on the workflow side), correct context-to-service binding and caller-owned disposal, but **Medium remains** because mocks verify only the requested factory arguments, not the effective Dataverse caller/impersonation, concurrent invocation isolation under load, or access-denied behaviour. Verify effective identity and access boundaries in an isolated registered plug-in/workflow environment before any elevated operation is approved. No elevated business operation, external connection, credentials or new authentication mechanism is introduced.

### Illustrative example (already present on the branch, not registered with Dataverse)

`WorkOrderQueries` → `WorkOrderApplicationService` is a deliberately **read-only, unregistered, no-op-on-write** example: it retrieves only the primary ID via a bounded `QueryExpression` and returns synchronously. The illustrative plug-in handler validates `Create`/`msdyn_workorder` and traces that it made no change; it has no concrete `IPlugin` entry point or registered step. ## Consequences

- **Positive**: Aligning types and handlers with their owning layers reduces shared-project ambiguity, keeps plug-in host concerns out of `Application`, makes persistence effects clearer to callers, and ensures analyser warnings in migrated code are addressed rather than carried forward.

- **Cost impact (licences, connectors, infrastructure, maintenance)**: No new licence, connector, runtime dependency or infrastructure cost. There is one-off engineering and regression-test effort per migration; ongoing maintenance should improve through clearer ownership.
- **Impact on other solutions/environments**: No Dataverse schema, registration or deployed behaviour changes are authorised by this ADR update. Shared-source namespace changes require checking all consumers and rebuilding both deployment heads and the UnitTest/Container path; preserve assembly and registered entry-point identities. The existing ephemeral Dev/Test and Package Deployer model is unchanged.
- **Technical debt impact**: **Reduces** after migrated code and its direct tests have no outstanding analyser warnings; unrelated baseline warnings remain separately tracked. Until a representative slice is migrated, this outcome is not yet verified.
- **Architecture debt impact**: **Reduces**. ## Key Technical Assessments Requested

**1. Synchronous handler contract.** `IPluginHandler.Execute()` should return `void`, and `PluginBase<THandler>.Execute` should invoke it directly. The Dataverse entry point and SDK calls in scope are synchronous; there is no asynchronous requirement. A `Task` return plus `GetAwaiter().GetResult()` would add sync-over-async complexity without benefit. Handlers must not use `async void`, background work, or parallel SDK calls; Dataverse explicitly disallows asynchronous/parallel execution in plug-ins and workflow activities.

**2. Scope ownership.** `PluginBase<THandler>.Execute` and `WorkflowActivityBase<THandler>`'s sealed `Execute` each own their invocation scope: it is created and disposed (via `using`/explicit `Dispose`) entirely within one `Execute` call, and nothing escapes it — the scope is never cached, stored in a field, or reused across invocations. Both adapters apply the agreed execution/cleanup failure precedence (see above) rather than allowing a disposal exception to mask an execution failure. Each deployment head owns one registration-only `Lazy<PluginContainer>` root (`PluginCompositionRoot`/`WorkflowCompositionRoot`); neither root is yet referenced by a Dataverse-registered component, and neither ever holds a borrowed per-execution instance.

**3. Logger availability.** `ILogger` is registered on the scope **only when Dataverse's `IServiceProvider` actually supplies one** (environment/Application Insights-dependent) and is never available to a workflow-activity-style scope at all. A handler with a required `ILogger` dependency is therefore implicitly plugin-only and will fail fast, by design, if reused from a context that cannot provide it.

**4. CWA compatibility.** Confirmed by test: a scope built the CWA way (`IWorkflowContext`/`IOrganizationService`/`ITracingService` only) successfully resolves a shared `Application`-layer service and explicitly fails to resolve `IPluginExecutionContext`. CWAs also execute synchronously. The implemented `WorkflowActivityBase<THandler>` centralises resolution and lifecycle management; a constructor-injected handler reads/writes the concrete activity arguments using the current `CodeActivityContext` and calls synchronous application services. Its lifecycle, exact host-created-activity binding, argument mapping, reused/concurrent-invocation isolation and execution/cleanup failure precedence are now verified by unit tests driving the activity through a real `System.Activities.WorkflowInvoker` (`WorkflowActivityScaffoldTests`); no activity is registered with Dataverse and no isolated-environment/registered execution has verified it.

**5. Shared-source cross-assembly type identity.** Because `Defra.Imports.Application`/`Dataverse`/`Infrastructure` are Shared Projects (not real assemblies), every type they declare is **compiled separately into whichever head assembly imports it**. In Release/Debug, `Plugins.dll` and `Workflows.dll` each get their own private copy of e.g. `PluginContainer` — these are different CLR `Type` objects despite the identical name, so an instance built in one is never assignment-compatible with the other; this is fine only because nothing is ever passed between the two deployed assemblies. Under `UnitTest`, both head projects instead reference `Container.dll`, giving `UnitTests.dll` the same copy the (test-configuration) head assemblies use — preserving type identity for test assertions. The inherited trade-off: unit tests only ever exercise the IL compiled into `Container.dll`, never the literal bytes shipped in the real Release `Plugins.dll`/`Workflows.dll`. This risk already existed for `Model`/`BusinessLogic`/`Repositories` (the `Model` types now arrive via `Dataverse`) and is unchanged in kind, only in surface area, by adding three more shared projects to the same mechanism — see Risk Register.

## Migration & Usage Guidance

To adopt this pattern for a **real** plug-in step (none exist yet):

1. Add a `WorkOrders`/`<YourDomain>` folder convention for application services in `Application`, Dataverse queries/models in `Dataverse`, and plug-in handlers in `Plugins` (workflow activity handlers remain in `Workflows`), following the existing example's use-case shape.
2. In the `Plugins` project, add the new handler and its type registrations to the single `internal static PluginCompositionRoot` shared by all plug-in classes. Create this root once for the assembly, using a `private static readonly Lazy<PluginContainer>` built by a `BuildRoot()` method that only calls `Register<TInterface, TImplementation>()`/`Register<TImplementation>()` — **never** capture a per-execution instance in this method or field. Do not add a per-plug-in composition-root class or repeat common registrations.
3. For a new entry point, add a concrete `public sealed class <UtilityName>Plugin : PluginBase<YourHandler>` with a parameterless constructor calling `base(PluginCompositionRoot.Root)`. Name it for its utility, not its triggering message/stage. Use the Plug-in Registration Tool to configure the appropriate steps and images in the isolated development environment; capture them in the owning solution for deployment rather than expressing registrations in code attributes.
For an existing entry point, refactor behind its existing type identity and registration without renaming it or re-registering its steps.

4. Write `YourHandler : IPluginHandler` in the `Plugins` head assembly, taking its dependencies (an `Application` service, `IPluginExecution`, etc.) via constructor injection. Validate the expected step context/registration contract, apply plug-in-context changes such as target/shared-variable updates, and call coarse application methods. Keep reusable business rules, and the reads and writes that belong to a use case, in application services rather than the handler. Implement synchronous `void Execute()`; do not use `async void`, `Task`, background work, or parallel SDK calls.
5. For a new CWA, use the implemented `WorkflowActivityBase<THandler>`; do not use `PluginBase<THandler>`/`IPluginHandler` or repeat scope creation. Register its workflow handler and dependencies in the single `WorkflowCompositionRoot` shared by all activities. Pass that root from the activity's parameterless constructor and bind `this` under its concrete activity type in `RegisterActivity(scope)`. The handler receives that activity, `CodeActivityContext` and its services through constructor injection, then validates inputs and sets outputs in synchronous `Execute()`. Preserve existing activity contracts on migration.
6. Keep the roots in their respective deployed head projects; do not reference the plug-in head assembly from the workflow head. The following snippets mirror the real, implemented source already on this branch (`PluginCompositionRoot.cs`, `WorkOrderInitialisationPlugin.cs`, `WorkflowCompositionRoot.cs`, `LoadWorkOrderContextActivity.cs`) — simplified only by omitting the `IImportsContextFactory`/`ImportsContext` registrations each real root also includes (see Execution identity above); this scaffold deliberately adds no discoverable concrete plug-in or registration, because neither composition root nor example type is referenced by any Dataverse solution/registration metadata.

### Plug-in composition example

The single static plug-in root caches registration metadata only and is shared by every plug-in class in `Plugins.dll`. Add registrations for later handlers to its `BuildRoot()`; do not create a `WorkOrderCompositionRoot` or another root per plug-in. The unused non-generic plug-in base has been removed as part of this scaffold's implementation (confirmed deleted by repository-wide source search — see Technical and Architecture Debt Register); the qualified base name below identifies the new infrastructure adapter. In the target layout, the handler import is from the plug-in head assembly, not `Application`; the existing illustrative handler file must move from its current Application location when the associated refactoring is made.

```csharp
using System;
using Defra.Imports.Plugins.Handlers;
using Defra.Imports.Application.WorkOrders;
using Defra.Imports.Dataverse.Queries;
using Defra.Imports.Infrastructure.DependencyInjection;

internal static class PluginCompositionRoot
{
    private static readonly Lazy<PluginContainer> RootValue =
        new Lazy<PluginContainer>(BuildRoot);

    internal static PluginContainer Root => RootValue.Value;

    private static PluginContainer BuildRoot()
    {
        var root = new PluginContainer();
        root.Register<IWorkOrderApplicationService, WorkOrderApplicationService>();
        root.Register<WorkOrderQueries>();
        root.Register<WorkOrderInitialisationHandler>();
        return root;
    }
}

// Documentation only: do not register this read-only illustration as a real business process.
public sealed class WorkOrderInitialisationPlugin :
    Defra.Imports.Infrastructure.Plugins.PluginBase<WorkOrderInitialisationHandler>
{
    public WorkOrderInitialisationPlugin()
        : base(PluginCompositionRoot.Root)
    {
    }
}
```

The adapter supplies the runtime services; the root never calls `GetService` or resolves a handler. The following handler is implemented and synchronous, and makes the shared application-service call explicit. It is the sole illustrative plug-in handler on this branch; the earlier Task-based `WorkOrderCreatedHandler` draft has been replaced by it, not kept as an additional handler alongside it.

```csharp
using System;
using Defra.Imports.Application.WorkOrders;
using Defra.Imports.Infrastructure.Plugins;

public sealed class WorkOrderInitialisationHandler : IPluginHandler
{
    private readonly IWorkOrderApplicationService application;
    private readonly IPluginExecution execution;

    public WorkOrderInitialisationHandler(
        IWorkOrderApplicationService application,
        IPluginExecution execution)
    {
        this.application = application ?? throw new ArgumentNullException(nameof(application));
        this.execution = execution ?? throw new ArgumentNullException(nameof(execution));
    }

    public void Execute()
    {
        if (this.execution.Context.MessageName != "Create" ||
            this.execution.Context.PrimaryEntityName != "msdyn_workorder")
        {
            throw new InvalidOperationException("This example requires a work order Create execution.");
        }

        this.application.GetInitializationContext(this.execution.Context.PrimaryEntityId);
        this.execution.Tracing.Trace("Work order example context loaded. No business changes were applied.");
    }
}
```

Use the actual domain table and approved business behaviour when introducing a real entry point. This remains a read-only illustration, not an implementation of work-order initialisation rules.

### Workflow adapter usage example (implemented; not registered with Dataverse)

This read-only example illustrates the implemented API and is present on this branch (verified by the `Defra.Imports.Workflows` Release build above), but it is not a registered component or approved business contract. `WorkflowCompositionRoot` is the single registration-only root in `Workflows`; it registers `LoadWorkOrderContextHandler`, `IWorkOrderApplicationService`/`WorkOrderApplicationService` and `WorkOrderQueries` once. It does **not** register `LoadWorkOrderContextActivity` as a constructible type. The base borrow-registers the current context and calls `RegisterActivity(scope)` before resolving the handler. Activity and handler are both defined in the workflow head project.

```csharp
using System;
using System.Activities;
using Defra.Imports.Application.WorkOrders;
using Defra.Imports.Dataverse.Queries;
using Defra.Imports.Infrastructure.DependencyInjection;
using Defra.Imports.Infrastructure.Workflows;
using Microsoft.Xrm.Sdk;
using Microsoft.Xrm.Sdk.Workflow;

internal static class WorkflowCompositionRoot
{
    private static readonly Lazy<PluginContainer> RootValue =
        new Lazy<PluginContainer>(BuildRoot);

    internal static PluginContainer Root => RootValue.Value;

    private static PluginContainer BuildRoot()
    {
        var root = new PluginContainer();
        root.Register<IWorkOrderApplicationService, WorkOrderApplicationService>();
        root.Register<WorkOrderQueries>();
        root.Register<LoadWorkOrderContextHandler>();
        return root;
    }
}

public sealed class LoadWorkOrderContextActivity :
    WorkflowActivityBase<LoadWorkOrderContextHandler>
{
    public LoadWorkOrderContextActivity()
        : base(WorkflowCompositionRoot.Root)
    {
    }

    [Input("Work order")]
    [ReferenceTarget("msdyn_workorder")]
    [RequiredArgument]
    public InArgument<EntityReference> WorkOrder { get; set; }

    [Output("Retrieved work order")]
    [ReferenceTarget("msdyn_workorder")]
    public OutArgument<EntityReference> RetrievedWorkOrder { get; set; }

    protected override void RegisterActivity(PluginContainer scope)
    {
        scope.Register<LoadWorkOrderContextActivity>(this);
    }
}

public sealed class LoadWorkOrderContextHandler : IWorkflowActivityHandler
{
    private readonly LoadWorkOrderContextActivity activity;
    private readonly CodeActivityContext context;
    private readonly IWorkOrderApplicationService application;

    public LoadWorkOrderContextHandler(
        LoadWorkOrderContextActivity activity,
        CodeActivityContext context,
        IWorkOrderApplicationService application)
    {
        this.activity = activity ?? throw new ArgumentNullException(nameof(activity));
        this.context = context ?? throw new ArgumentNullException(nameof(context));
        this.application = application ?? throw new ArgumentNullException(nameof(application));
    }

    public void Execute()
    {
        var workOrder = this.activity.WorkOrder.Get(this.context);
        if (workOrder == null || workOrder.Id == Guid.Empty)
        {
            throw new ArgumentException("A valid work order reference is required.");
        }

        var result = this.application.GetInitializationContext(workOrder.Id);
        this.activity.RetrievedWorkOrder.Set(
            this.context, new EntityReference("msdyn_workorder", result.WorkOrderId));
    }
}
```

The implemented base calls `scope.Register<CodeActivityContext>(context)`, invokes the activity binding hook, and then runs `scope.Resolve<THandler>().Execute()` inside the scope lifetime. Never manually construct a second activity or resolve the handler from the root. Neither `IPluginExecutionContext` nor `IPluginExecution` is registered in a workflow scope. Do not reference the plug-in head assembly or reuse its static container. Keep SDK argument attributes: they define workflow inputs/outputs, not deployment registrations. Production XML documentation is omitted from this illustrative snippet for brevity; the real source files carry full XML documentation. The scaffold Release builds reported no SA1642/SA1615 warnings; unrelated repository warnings are outside that targeted claim.

**Shared business-logic path:** both entry points resolve `IWorkOrderApplicationService` to the same shared-source `WorkOrderApplicationService`, which uses the same `WorkOrderQueries` and returns `WorkOrderInitializationContext`:

- Plug-in: `WorkOrderInitialisationPlugin` → `WorkOrderInitialisationHandler` → `WorkOrderApplicationService` → `WorkOrderQueries`.
- Workflow: `LoadWorkOrderContextActivity` → `LoadWorkOrderContextHandler` → `WorkOrderApplicationService` → `WorkOrderQueries`.

Only the boundary adapters differ: the plug-in handler obtains the ID from `IPluginExecution`; the workflow handler obtains it from the activity input and maps the returned projection to an output. Neither duplicates the application/query logic, and the workflow does not reuse a plug-in-specific handler. The two deployment heads compile the same shared-source business classes but own separate roots, execution scopes and service instances; no runtime object is shared across the assemblies. Both examples are read-only and do not introduce work-order business rules.

### Incremental migration recommendations

- Leave existing `BusinessLogic`, `Repositories`, live plug-in base classes and registrations untouched until a separately scoped business change adopts this pattern. The sole removal in this scaffolding implementation is the unused non-generic `Defra.Imports.Plugins.PluginBase` and its associated context/tracing helpers, as specified above.
- Start with one small use case and preserve its entry-point identities, registrations and workflow argument contracts. Characterise successful and failure behaviour, target mutations, outputs and persistence timing before replacing its composition. Apply the confirmed migration constraints above; raise suspected bugs for approval rather than fixing them silently.
- Move query construction and SDK-specific helpers into `Dataverse`; move orchestration and business rules into `Application`. Prefer business-oriented query methods over a generic repository layer.
- The `Model` migration is complete: the old `Model` source is in `Dataverse.Model` (generated), `Constants` and `ReferenceData` are in `Application`, and the `Model` project is retired. As each use case migrates, move plug-in handlers into `Plugins`; keep workflow activity handlers with their activities in `Workflows`. Update namespaces and shared-project inclusion lists atomically and remove the old entries.
- Resolve pre-existing analyser warnings in the source being refactored and any warnings introduced by the migration. Do not add broad suppressions; do not make unrelated repository-wide warning cleanup an implicit prerequisite. Record and review any unrelated baseline warnings separately.
- Keep persistence effects explicit in application-facing method contracts and names. A persistence operation delegates its actual SDK write to the Dataverse boundary; an entity-hydration operation returns the modified entity without persisting it. Characterise and test both outcomes, especially when the returned entity is intended to be the existing pre-operation target.
- For every migrated source file, update its owning `.projitems` and remove its old inclusion in the same change. Keep new shared imports conditional in both deployment heads, so UnitTest still compiles shared types once through Container.
- Test the first adoption in an isolated Dataverse environment, including transaction behaviour, exception handling, tracing and CWA reuse where relevant. Local unit tests and self-contained builds do not replace this platform verification.
- When committing changes outside solution metadata, include the appropriate `+solutionVer(<solutionName>): patch` trailer (or a higher increment where warranted). Link the actual Azure Boards item using `AB#` in both PR title and body; no identifier was supplied here.
